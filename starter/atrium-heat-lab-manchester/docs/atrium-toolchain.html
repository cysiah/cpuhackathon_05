Atrium
toolchain

How geometry travels from the Rhino model into JSON, what each file holds, and how the web app turns those files into scores, proxies and approximations.

The chain at a glance

The web app never opens a Rhino file. Geometry and results are written to JSON by Python scripts, the EnergyPlus sweep adds simulated results, and the browser reads only JSON. Each link in the chain can be rerun on its own.

The three exporters

All three run inside Rhino 8 from the ScriptEditor. Model units are converted to metres and Rhino coordinates are kept, with true north at 60.9° anticlockwise from +Y.

Inside the atrium exporter

Each face of the atrium is given a role by layer or by key. A key in Attribute User Text takes precedence over the layer, so objects in the shared RhinoSync model can be tagged without being moved.

RoleLayerKeyContentsEnergyPlus boundary
ExposedATRIUM::Exposedatrium_role = exposedRoof slopes, clerestories, gablesOutdoors, glazing allowed
MassATRIUM::Massatrium_role = massFloor and walls to the rest of the buildingAdiabatic thermal mass
GlazingATRIUM::Glazingatrium_role = glazingPanes lying on Exposed facesGlazed area of the host face

What the script does, in order

  1. Tagged objects are collected; keys are read first, layers second. With nothing tagged, the script offers to create the three layers or to switch to picking faces interactively.
  2. Exposed and Mass objects are broken into single faces and joined. Anything that does not join into one closed volume stops the export, and the offending objects are left selected.
  3. Each glazing piece is assigned to the nearest face within 0.5 m, and its area is added to that face. Pieces further away are reported and ignored.
  4. Each face’s vertices are ordered to point out of the zone, tested by checking whether a point just off the face lies inside the volume.
  5. Faces are typed by their normal: pointing down (z < −0.7) becomes floor, pointing up (z > 0.3) becomes roof, the rest walls. A glazed face tagged as Mass is promoted to Exposed, with a warning.
  6. The faces and a summary (floor area, volume, glass area, internal area, bounding box) are written to JSON, and the same areas are written into baseline.json.

Warnings are printed for faces that are not planar, faces with holes (the holes are ignored), and glazing that misses every face. The export is reversed by deleting atrium_geometry.json, which returns the sweep to its built-in box.

From geometry to simulated scores

sweep_atrium.py builds one well-mixed EnergyPlus zone per design. When atrium_geometry.json exists its faces are used; otherwise the built-in box is. On each exposed face, glazing is applied as a ratio of glazed area to face area, capped at 0.99. The roof screen is placed 1.5 m above the highest point of the zone, extended 2 m beyond its footprint. Every combination of the five lever levels is simulated, plus 40 random designs between the levels, which are used only to measure interpolation error. The last full run took 1,512 s (about 25 minutes) on 14 cores.

# Mac: quick test (32 designs, about a minute), then the full grid
~/ladybug_tools/python/bin/python3 tools/sweep_atrium.py --quick
~/ladybug_tools/python/bin/python3 tools/sweep_atrium.py --workers 6

# Windows
"C:\Program Files\ladybug_tools\python\python.exe" tools\sweep_atrium.py --quick

data/sweep.json is overwritten by every run, including --quick, so a copy is kept beforehand.

How the analyses are structured

Inside the browser, every number passes through the same four layers. Each layer adds a kind of result and a source tag, so a value on screen can always be traced back to where it came from.

Layer 1Simulated results
3,125 EnergyPlus runs on a full 5 × 5 × 5 × 5 × 5 grid of the levers, each with hourly operative temperature for the hot week.
Filedata/sweep.json EnergyPlus
Layer 2Surrogate
Multilinear interpolation between the 32 grid corners that surround any design. Exact on the grid. Checked against the 40 off-grid runs: 4.8 K·h RMSE, 20.4 K·h worst, +2.5 K·h bias.
CodeH.Surrogate in js/model.js
Layer 3Metrics
Each metric is a small object: label, unit, better direction, source tag and a function of the design and its result. Registering one makes it available to the explorer, the Pareto front and the sensitivity charts at once.
CodeH.metrics and H.extraMetrics
Layer 4Mechanisms
Post-processing and simple physics on top of the results: TM52, heat balance, stack flow, winter solar, cooling, fan energy, and approximations of interventions outside the sweep.
Codejs/mechanisms.js derived proxy approx

Catalogue labels

Every analysis and intervention in data/design_catalogue.json carries a now block with a level, the mechanism, where it appears in the app, and its limits. Items the current model cannot answer are kept on the list with what they would need.

Adding a metric

A new analysis built only from existing results needs no simulation. The procedure:

  1. Write the calculation as a function in js/mechanisms.js, taking the design d and its result r (which includes r.operative, the 168 hourly temperatures).
  2. Register it in H.extraMetrics() with a label, unit, better direction and source tag, as below.
  3. Add the item, or update its now block, in data/design_catalogue.json.
  4. Run python3 tools/build_docs.py to refresh docs/ANALYSES.md, then refresh the browser.
morning: { label: 'Atrium before opening (night flush)', unit: '°C', better: 'low',
           source: 'derived', get: (d, r) => H.nightFlush(r.operative).morning },
